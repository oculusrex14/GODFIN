# Durable jobs, local diagnostics, and performance evidence

Recorded: 11 August 2026 (Asia/Kolkata)

This record covers repository work for `GF-JOB-001`, `GF-OBS-001`, and
`GF-PERF-001`. It does not claim completion of the final browser or native
cross-platform package matrices.

## Durable local work

GODFIN now persists long-running work in the local SQLite database. The queue
stores only bounded job metadata and payloads; it does not transmit telemetry.

- Active work is claimed through a short `BEGIN IMMEDIATE` lease operation.
- One unique active key prevents duplicate Gmail ingestion, backups, digests,
  or embedding setup across multiple backend processes.
- The queue accepts at most 100 active jobs and runs at most two concurrently.
- Writes retry a short SQLite lock with bounded exponential backoff. Handler
  retries use deterministic exponential backoff plus jitter and poison the job
  after its configured attempt limit.
- Lease heartbeat and expiry recover work abandoned by a process crash. Startup
  performs lease recovery synchronously, so a missing queue schema cannot be
  misreported as a healthy worker.
- Cooperative cancellation is durable. Completed, failed, cancelled, and
  poisoned work releases its active key without deleting its audit record.
- Public job status contains progress, safe operation names, stable failure
  codes, retry time, and a bounded result. It excludes credentials, source
  payload text, exception strings, and local paths.

The durable handlers cover first Gmail sync, date-range Gmail sync, scheduled
Gmail sync, automatic backup, weekly digest, and embedding setup. Gmail network
fetches happen after the cursor-reading SQLite transaction is rolled back;
message writes then use a separate session. Model generation and Gmail network
calls therefore do not hold a database transaction open.

## Liveness, readiness, and support diagnostics

`GET /api/v1/health` is process liveness only. It intentionally does not touch
SQLite. `GET /api/v1/ready` checks the database, schema revision, and application
lifecycle. Scheduler and worker failures are reported as optional degradation:
the deterministic local ledger remains usable while those services recover.

Each HTTP request receives a new random support ID generated by GODFIN. Caller
values are never trusted as correlation IDs. The same ID is included in normal
response headers, safe error payloads, and a job enqueued by that request.

Local metrics are bounded, aggregate-only, and process-lifetime only. They keep
operation names, request counts, server-error counts, averages, maxima, and a
coarse p95 upper bound. They never retain URLs, query values, request bodies,
financial values, or user identifiers, and `remote_telemetry` is explicitly
false.

The authenticated Settings download produces
`godfin-support-diagnostics.json`. It includes application/readiness state,
backup protection, aggregate queue state, and aggregate request metrics. It
does not include logs, payloads, job results, database paths, Gmail state,
license keys, tokens, PIN material, transaction data, or account data.

Structured logs rotate locally beside the application database by default.
The directory is restricted to mode `0700` and the log to `0600` where the OS
supports POSIX permissions. Both JSON and console formatters redact bearer
tokens, common secret fields and query parameters, email addresses, phone
numbers, long number sequences, and private filesystem paths.

## Enforced performance contract

`performance/budgets.json` is now schema version 2. Every budget declares its
unit and the test or package verifier that consumes it. CI runs
`scripts/verify_performance_contract.py`, which fails if a budget is invalid,
unreferenced, or points outside the repository. The effective limit is the
smaller of the absolute maximum and accepted baseline plus 15%.

The backend suite now enforces latency and SELECT-count limits for a 10,000-row
dashboard, report summary, behavior insights, and a 1,000-merchant recurring
scan. Existing gates continue to cover 10,000-row transaction filtering and a
1,000-row structured import. Desktop package verification consumes cold-start
and idle-memory limits; Playwright consumes the common-navigation p95 limit.

Measured on the baseline Apple Silicon host using Python 3.12.13:

| Operation | Dataset | Time | SELECT statements |
| --- | ---: | ---: | ---: |
| Dashboard | 10,000 rows | 16.74 ms | 5 |
| Report summary | 10,000 rows | 17.32 ms | 6 |
| Behavior insights | 10,000 rows | 164.88 ms | 5 |
| Recurring detection | 1,000 merchants / 4,000 rows | 415.25 ms | 3 |

The recurring detector is batch-based: the 1,000-merchant acceptance test
replaces the baseline audit's 952-query result with three SELECT statements.

`scripts/benchmark_large_ledger.py` creates temporary deterministic ledgers and
never opens the configured GODFIN database. The recorded evidence is
`docs/production-remediation/evidence/large-ledger-macos-arm64.json`:

| Rows | Dashboard | Report | Behavior insights | Max process RSS |
| ---: | ---: | ---: | ---: | ---: |
| 10,000 | 16.74 ms | 17.32 ms | 164.88 ms | 158.5 MiB |
| 50,000 | 145.89 ms | 155.67 ms | 820.76 ms | 290.5 MiB |
| 100,000 | 327.31 ms | 339.24 ms | 1,782.09 ms | 459.9 MiB |

Query counts remain constant at 5, 6, and 5 respectively across those sizes.
The memory figure is a process high-water mark while the benchmark builds three
databases sequentially; it is not an Electron idle-memory claim.
