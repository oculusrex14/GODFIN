# Dependency, supply-chain, and local package evidence

Recorded: 16 August 2026 (Asia/Kolkata)

This record covers repository work for `GF-DEP-001`, `GF-LIC-001`,
`GF-REL-001`, and the package portion of `GF-ASSET-001`. It is evidence for a
private local candidate, not permission to publish an installer or update feed.

## Dependency boundaries

GODFIN now has three separately generated, universal Python 3.12 hash locks:

- `requirements-lock.txt` contains only application runtime dependencies.
- `requirements-test-lock.txt` inherits the exact runtime pins and adds test
  tooling.
- `requirements-build-lock.txt` inherits the exact runtime pins and adds only
  frozen-build tooling.

The runtime no longer carries the retired Anthropic, Google Generative AI, or
OpenAI SDKs, Python Levenshtein, pytest, or the compatibility HTTP test stack.
Provider calls use the existing bounded REST adapters. The official Google API
client remains a runtime dependency because Gmail ingestion imports it; a clean
environment exposed that it had previously been supplied only by the developer
machine. All three locks now include and freeze that client and its transitive
dependencies.

`scripts/verify_dependency_boundaries.py` fails when a production dependency
enters the wrong surface, a lock is not generated by the reviewed Python 3.12
command, a requirement lacks hashes, runtime pins differ across inherited
locks, or a retired/test-only module is imported by runtime source.

The weekly private lock-refresh workflow opens a review PR even when a changed
version needs human license work. The PR remains fail-closed: vulnerability,
license, SBOM, notice, frozen-package, and required CI gates must pass before
merge. `CODEOWNERS` requires the repository owner to review workflow, lock,
SBOM, notice, policy, and provenance changes.

## Vulnerability and license inventory

The deterministic CycloneDX 1.6 SBOM contains 1,008 unique components: 904 npm
and 104 PyPI packages. Every component has a version, package URL, integrity
hash where its ecosystem provides one, dependency surface, scope, and resolved
license expression. The exact SBOM SHA-256 is:

`5d608767335fb9a259832b2d7e364a78af1a781890be5a923624f0766f44175b`

`THIRD_PARTY_NOTICES.md` is generated from the same exact lock inputs. The
generator rejects unreviewed Python versions, missing npm license metadata,
unresolved license IDs, prohibited licenses, stale review entries, and stale
outputs. Private-package verification requires byte-identical copies of the
PolyForm Noncommercial license, notices, SBOM, and legal-clearance record.

Four npm production trees report zero known vulnerabilities. `pip-audit 2.10.1`
reports zero known vulnerabilities in each Python lock after applying the one
documented, source-qualified temporary exception for `cryptography 49.0.0`
advisory `PYSEC-2026-3552`: GODFIN does not import or call the affected PKCS#7
decrypt APIs. Every other advisory remains fatal.

Nineteen unique components require a conditional-license review. Most are
MPL-licensed build, browser-test, or data packages; `fpdf2 2.8.7` is
LGPL-3.0-only. Repository automation cannot provide qualified legal advice.
Accordingly, `supply-chain/legal-clearance.json` remains `pending`, and
`verify_supply_chain_artifacts.py --promotion` blocks public promotion until a
qualified reviewer approves the exact SBOM hash and release version.

## Release provenance and immutability

The draft-release workflow checks out the exact tag, verifies that tag against
the desktop version and commit, builds on native OS/architecture runners, and
refuses to replace an existing release. Every GitHub Action is pinned to a
verified immutable 40-character commit, with its release tag retained only as
a review comment. The workflow stages uniquely named assets and
binds every exact byte to an in-toto Statement v1 with a SLSA provenance v1
predicate containing the repository, full commit, ref, workflow, run, and
attempt. A verifier rejects changed, missing, or late-added files.

The promotion workflow verifies checksums, the exact asset inventory and
provenance, SBOM/notices/legal evidence, platform metadata, and staged-rollout
confirmation before it can update the feed. Optional GitHub artifact
attestations are enabled only for a private GitHub Enterprise repository that
supports them; the repository's own exact provenance remains mandatory in all
cases. Rollback verifies both current and target compatibility/provenance before
publishing prior metadata.

  materials.
- Apple Developer ID signing and notarization on macOS arm64 and x64.
- Windows Authenticode/SmartScreen evidence on a clean Windows x64 machine.
- Linux x64 AppImage/deb installation, sandbox, permissions, and update tests.
- Native clean-machine upgrade, rollback, uninstall/data-retention, offline
  first-run, non-ASCII path, and endpoint-security testing on every platform.
- Private GitHub branch protection/ruleset configuration and, if licensed,
  GitHub Enterprise artifact attestations.
- R2 release storage, update-feed credentials, staged health review, and owner
  authorization. No workflow run or artifact described here is a public launch.
